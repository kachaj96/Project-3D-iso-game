# Research and technology stack

Researched October 2026. Facts marked **[verified]** come from official docs or the vendor. Facts marked **[secondary]** come from third-party articles and should be rechecked before you spend money on them. Everything else is a recommendation.

## 1. What the existing `kachaj96/Game` project tells us

I inspected the `Game` repo before choosing anything, because it changes the picture a lot.

- It is "Natalis: Księga Latarni": about 20,000 lines of vanilla JavaScript on HTML5 Canvas, wrapped as an Android app with Capacitor 6. It has 27 unit test files that pass, a Playwright smoke test, and a GitHub Actions workflow that builds a debug APK on every push.
- It already contains a Dofus-style turn-based combat system: action points, movement points, line of sight (`los()` in `www/js/dungeon.js`), initiative order, a placement phase, seeded RNG, and an offline balance simulator (`tools/balance_report.mjs`, `tools/tune_balance.mjs`).
- Its combat logic is written the right way: pure functions over plain state that return events. That is exactly the pattern this new project needs for co-op later.
- Its `CLAUDE.md` says isometry was deliberately left out and planned as a separate project, "Natalis 2". This repo is effectively that project.
- Art is generated by Python/Pillow scripts (`tools/make_*.py`) plus the Sprout Lands pack. Its own `ROADMAP.md` names graphics for new regions as "the only thing that can block the next stages".

What this means for you:

1. You are not a typical beginner. You have already directed an AI to build and ship a large, tested game. Your real gaps are the engine editor, art production and reading code well enough to catch AI mistakes.
2. The design knowledge (combat rules, balance targets, the simulator approach, the lore discipline) carries over. The code does not, because the new project needs an engine with an editor, isometric rendering, lighting and networking.
3. Art was already the bottleneck in the previous project, and a hand-illustrated isometric game makes it far harder. Art is the main risk of this project, not code.

Two housekeeping issues in `Game` worth fixing regardless: the release keystore and its password are committed (`android/app/build.gradle`, `android/app/mala-farma.keystore`), and the Sprout Lands zip is committed even though `.gitignore` says the license forbids redistribution. The repo is private, so this is low risk today, but it becomes a real problem the day the repo goes public. In this project, signing keys live in GitHub Secrets from day one.

## 2. Engine

### Candidates

| | Godot 4.7 | Unity 6 | Web stack (PixiJS/Phaser + Capacitor) | Unreal 5 |
|---|---|---|---|---|
| Cost | Free, MIT license | Free under $200k revenue/funding, Made with Unity splash optional in Unity 6 **[verified]** | Free | Free, 5% royalty over $1M |
| 2D isometric | Built-in isometric TileMapLayer, Y-sort, 2D lights with normal maps | Good (Tilemap iso, 2D URP lights) | You build depth sorting, lighting and tools yourself | Poor fit for 2D |
| Level editor for hand-made maps | Yes | Yes | No (Tiled as external editor) | Yes |
| Android | One-click deploy and APK/AAB export, small builds | Mature, larger builds | Your current setup | Heavy, poor fit |
| LAN co-op | ENet high-level multiplayer built in, UDP for discovery **[verified]** | Netcode for GameObjects + Unity Transport | Needs community Capacitor UDP/TCP plugins **[secondary]** | Built in, overkill |
| AI coding fit | Scripts, scenes (`.tscn`) and resources (`.tres`) are plain text Claude can read and edit. Main hazard: models mixing Godot 3 and 4 syntax | C# is excellent for AI, but scenes and prefabs are noisy YAML Claude should not edit by hand | Best AI fluency of all, and your proven workflow | C++/Blueprints, weak fit |
| Beginner fit | Small, fast editor, very good docs | Larger, heavier, more concepts | No editor to learn, but you must build the engine parts | Steep |

### Recommendation: Godot 4.7 (latest 4.7.x stable) with typed GDScript

Why Godot wins for this game specifically:

- **Hand-crafted map screens need an editor.** A Dofus-style world is hundreds of hand-placed screens. Painting tiles and placing props in Godot's editor is far faster than describing them in code or JSON, which is what the old project did.
- **The dark atmosphere needs 2D lighting.** Torches, glowing spells, fog and day/night are built into Godot (PointLight2D, CanvasModulate, normal maps, shaders). On Canvas you would build that yourself.
- **Co-op without third-party plugins.** ENet over local Wi-Fi works with no internet. Discovery uses UDP broadcast. Android needs the `INTERNET` permission, and some devices need `CHANGE_WIFI_MULTICAST_STATE` to receive broadcasts **[verified]**.
- **Everything is text.** Claude Code can inspect and modify scripts, scenes and data resources, and CI can run Godot headless for tests and APK exports, just like your current workflow.
- **Use the Compatibility renderer.** Godot's docs recommend it for 2D and for the widest device support **[verified]**.
- **Godot 4.7 is current:** 4.7 stable shipped mid-2026, followed by maintenance releases 4.7.1 and 4.7.2 **[verified for 4.7.1, secondary for dates]**. Use the newest 4.7.x patch and do not upgrade minor versions in the middle of a milestone.

Use GDScript, not C#. It needs no .NET setup, Android export is simplest, and the docs and examples are GDScript-first. Turn on static typing warnings so the editor catches type mistakes early.

**Runner-up: Unity 6.** Pick it only if you later need something Godot cannot do. Dofus itself moved from Flash to Unity in December 2024 **[verified]**, so it can obviously do this genre, but that took a professional team of around thirty developers **[secondary]**. For a solo beginner, Unity's heavier editor and binary-ish scene workflow cost more than they give back.

**Not chosen: staying on JavaScript.** It is the strongest alternative because of your track record. It loses on three points that matter here: no map editor, no built-in lighting, and LAN networking that depends on small community plugins. If the Godot editor turns out to be a wall for you after Milestone 2, revisit this decision (see `DECISIONS.md`).

## 3. Art pipeline

Your target (stylized, illustrated, Dofus readability, darker Souls/Diablo mood, distinct regions) is the most expensive kind of 2D art. No tool produces it consistently at scale today. The realistic answer is a hybrid pipeline that you lock in after a short style test. Details are in `ART_PIPELINE.md`.

Options compared:

| Approach | Look | Scales to many characters and gear? | Beginner effort | Notes |
|---|---|---|---|---|
| **A. Cutout (paper-doll) 2D rig**: painted body parts, animated with bones | Closest to Dofus/Wakfu | Yes. Swapping a hat or cape is swapping one texture | Medium | Godot's built-in Skeleton2D + AnimationPlayer is free. Spine Essential is $69 one-time if Godot's tools feel clunky **[verified]** |
| **B. Pre-rendered 3D**: model in Blender, render to sprite sheets from the iso angle | Clean, consistent, can be toon-shaded | Very well. Any number of directions and animations | High (Blender) | Proven workflow, add-ons like SpriteStar automate cameras **[secondary]** |
| **C. AI pixel art** (PixelLab, Retro Diffusion) | Pixel art, not illustrated | Good, these tools generate rotations and animations **[secondary]** | Low | Fastest path, but it is not the look you described |
| **D. Frame-by-frame painted animation** | Best possible | No | Very high | Not realistic solo |

**Recommendation:** A for characters and monsters, AI-assisted painting plus manual cleanup for tiles and props, and B kept as the fallback if cutout animation looks stiff. Decide after a two-week style spike (Roadmap Milestone 1), not before.

AI image tools: start with a paid cloud service that can train a custom style model on your own reference images (Scenario is one example, roughly $15-45/month with custom training on the mid tier **[secondary, recheck]**). Running models locally (ComfyUI with SDXL plus your own LoRA) is free per image but needs an NVIDIA GPU with 16 GB VRAM to train comfortably **[secondary]**. Use the cloud for the first one or two months and only buy a GPU if you are generating daily.

Legal points before any public release:

- In the US, pure prompt output is not copyrightable. Human selection, arrangement and modification can be **[verified, US Copyright Office 2025 report]**. Paint over and edit everything you ship, and keep the source files. That is better for consistency anyway.
- Google Play's AI-generated content policy targets apps that generate content for users, not games made with AI-assisted art **[verified]**. Recheck Play's policies before release.
- Read each AI tool's terms for commercial use. Free tiers often exclude it.

## 4. AI coding tools

- **Claude Code: keep it as the primary tool.** You already know it, it works in the terminal next to Godot, and it can run Godot headless for tests and checks. Start on Pro ($20/month). Move to Max 5x ($100/month) only if you hit the limits on most working days **[secondary, check claude.com/pricing]**.
- **Godot MCP servers:** several community servers let Claude run scenes, run tests and read errors **[secondary]**. Not needed at first. Claude can run `godot --headless` commands directly. Revisit in Milestone 3 if the error round-trips get tedious.
- **Alternatives** (Cursor, Copilot, Codex CLI, Gemini CLI) do not add enough to justify a second subscription. Pick one tool and learn it well.

The main AI risk in Godot: models mix Godot 3 and Godot 4 APIs (`KinematicBody2D` vs `CharacterBody2D`, `yield` vs `await`, `TileMap` vs `TileMapLayer`). `CLAUDE.md` pins the version and forbids Godot 3 APIs. CI runs a headless parse check so these errors fail fast.

## 6. Local co-op networking

- **Model:** one phone hosts and is the authority for the world and combat. The other phone joins as a client. No dedicated server, no internet required.
- **Transport:** `ENetMultiplayerPeer` (reliable UDP) for the game. A small `PacketPeerUDP` broadcast on a fixed port so the joining phone can find the host without typing an IP address **[verified]**. Keep a manual "enter IP" fallback, because some routers and hotspots block broadcast.
- **Phone hotspot:** the hotspot phone gets a LAN IP and the other phone connects to it as normal Wi-Fi. This should work with ENet. I found no source confirming broadcast discovery on every Android hotspot, so it must be tested on your real phones in the co-op spike. That is why the manual IP fallback exists.
- **Why turn-based helps:** combat is a stream of small commands ("cast spell 3 at cell 47"), not 60 position updates per second. Exploration is click-to-cell movement. Both are cheap to sync and tolerant of Wi-Fi hiccups.
- **What makes it cheap later:** the architecture rules in `ARCHITECTURE.md` (commands in, events out, one authority, stable IDs, per-player saves). Following them in single-player costs almost nothing. Retrofitting them later means rewriting most systems.

## 7. Hardware

### PC

Godot itself is light: the editor needs around 3 GB of RAM, any 64-bit CPU with SSE4.2 and a Vulkan- or OpenGL-capable GPU **[verified]**. Android builds and Android Studio's SDK tools need more RAM and disk. Painting with AI tools in parallel needs more again.

| Tier | Spec | Good for |
|---|---|---|
| Minimum | 4-6 core CPU from the last ~6 years, 16 GB RAM, 512 GB SSD, any GPU | Godot, Android builds, Krita, cloud AI tools |
| **Recommended value** | 8-core CPU (Ryzen 7 or Core i7 class), **32 GB RAM**, 1 TB NVMe SSD, mid-range GPU | Everything comfortably, Blender if needed |
| Local AI art | As above with an **NVIDIA GPU with 16 GB VRAM** (RTX 5060 Ti 16 GB class) | Local image generation and LoRA training |

Buy the recommended tier without the 16 GB GPU first. Add the GPU only if cloud AI art bills exceed roughly the GPU's cost over a year, or if you want full control over your style model. Check current prices locally before buying.

A second monitor is the cheapest productivity upgrade: Godot on one screen, Claude Code and docs on the other.

### Android test devices

- **Milestones 0-5: one phone is enough.** Ideally a mid-range phone from the last 2-3 years. That is your main device.
- **Before the first playable release: add a cheap low-end phone** (around 4 GB RAM, budget chipset, 720p screen). It sets your performance floor. If the game runs at a stable 30+ fps there, it runs everywhere you care about.
- **Co-op spike: you need two physical devices.** The second can be that low-end phone. Emulators and two PC instances are fine for writing the code, but Wi-Fi discovery and hotspot behaviour only show up on real hardware.

## 8. Recommended stack summary

| Area | Choice |
|---|---|
| Engine | Godot 4.7.x stable, Compatibility renderer, typed GDScript |
| Platform | Android, landscape orientation, APK for testing, AAB for Play later |
| AI coding | Claude Code (Pro, upgrade only if needed) |
| Art | Style spike first. Expected: Krita + AI-assisted painting with a custom style model, cutout rigs in Godot |
| Dialogue | Dialogue Manager addon |
| Localization | gettext `.po`, English and Polish from the first UI string |
| Data | Godot custom Resources (`.tres`) with string IDs |
| Tests and CI | gdUnit4, GitHub Actions headless test + APK export |
| Co-op (later) | ENet host-client over local Wi-Fi, UDP broadcast discovery, manual IP fallback |
| Version control | Git + GitHub, Git LFS for source art |

Expected running cost: about $20/month for Claude Code plus $15-45/month for an AI art service during heavy art phases. One-time: Spine Essential ($69) only if needed, asset packs for audio and UI as needed.
